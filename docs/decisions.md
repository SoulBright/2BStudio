# Решения и допущения

То, чего в ТЗ нет однозначно, и что решил сам.

## Роли и доступ

- Роли в таблице `profiles`: `manager` (постановщик) и `executor` (исполнитель).
- Любой постановщик видит и может принимать/возвращать любую задачу, не только свою.
- Исполнитель на карточке объекта видит только **свои** задачи по этому объекту (иначе прочитал бы чужие — это запрещено ТЗ).
- Экран «Мои задачи» у исполнителя — его задачи; у постановщика тот же маршрут назван «Все задачи» и показывает всё.

## Задачи

- Исполнитель обязателен при создании; это пользователь с ролью `executor`.
- При создании статус всегда `new`, автор — текущий постановщик (триггеры в БД).
- Постановщик может менять название, описание и исполнителя. Статус через обычный UPDATE менять нельзя — только RPC `transition_task_status`.
- Комментарий обязателен только при переходе «На проверке» → «На доработке».

## История

- Каждая смена статуса пишется в `task_status_history`.
- Клиент не может вставить, изменить или удалить историю напрямую.
- При удалении задачи/объекта история удаляется каскадом (миграция `0004`): нельзя подделать историю отдельно, но сущность удаляется целиком вместе со следом.

## Auth и ключи

- Вход по email/паролю. Регистрация с клиента выключена, пользователи создаются вручную в панели Supabase.
- Сессия в `localStorage` (дефолт Supabase SPA). HttpOnly-cookie не использовал — нет своего backend/SSR.
- Во фронте только Publishable key. Secret / service_role в приложении не используются.

## UI

- Дизайн минимальный: один CSS, без UI-библиотек (по ТЗ дизайн не оценивается).
- Кнопки статусов в интерфейсе — подсказка; отказ при запрете всё равно приходит из базы.

## Что можно улучшить позже (не успел / вне объёма)

- Более удобные формы и валидация на клиенте
- Пагинация длинных списков
- Аудит изменений полей задачи (не только статусов)
- Cookie-сессии при появлении SSR/BFF
